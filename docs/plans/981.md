# 981: WAL disk warning and recovery on a real Host

Refs #744 (v1.0.0 bar test gap).

## Objective

`config.EventListener.OnLogDBDiskWarning` is documented to fire when WAL disk
usage crosses 85% of `HostConfig.MaxWALDiskSize`, documented as "the maximum
WAL directory size in bytes", and proposals are documented to be accepted
again once usage drops. Only `buildWALOptions` unit tests cover this. Prove it
end to end on a real Host with a running single-replica shard.

## Slices, in order

1. `pkg/host_disk_warning_test.go` (package quicraft), on a real Host with a
   small `MaxWALDiskSize` and NoSyncWAL:
   - (a) writing until usage passes 85% fires `OnLogDBDiskWarning` once per
     crossing, with `WALDir` equal to the Host's WAL directory, `UsedBytes`
     at or above 85% of `MaxBytes`, `MaxBytes` equal to the limit, and
     `Shards` containing the shard;
   - (b) after the full threshold is reached, a `SyncRequestSnapshot` with
     compaction and the WAL dropping the compacted segments bring usage below
     the threshold; `HealthCheck` reports `DiskOK` true; a new `SyncPropose`
     succeeds and its value reads back.
2. Per divergence from the docs: a failing `test:` commit, then a `fix:`
   commit in `pkg/host.go`.

## Known divergence (found while planning)

The WAL disk monitor measures the whole filesystem holding `WALDir` (statfs
used bytes), not the WAL directory. With any limit below the filesystem's used
bytes the full state trips on the first check, the warning never fires, and
usage can never fall by compaction. Fix: `buildWALOptions` passes a usage
function that sums the sizes of the files under `WALDir`.

## Out of scope

- The disk-full refusal itself (ErrDiskFull, OnLogDBDiskFull, DiskOK false),
  covered elsewhere.
- Any change outside `pkg/host.go` and the new test; any wire or on-disk
  format change.
