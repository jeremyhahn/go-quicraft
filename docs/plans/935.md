# Plan: #935 root-key re-key runbook against a real Host

Refs #744 (v1.0.0 bar test gap).

## Objective

docs/seal-barrier/user.md ("Respond to a key compromise", steps 1-4) and
docs/snapshots/user.md ("Re-key a snapshot") describe moving a Host's data to
a new root key: stop the Host, copy the WAL with `waldb.Reencrypt` passing a
snapshot function that calls `ReencryptSnapshotFile`, verify and swap the
destination into place, then start on the new barrier. Both functions have
unit tests; nothing runs the documented sequence against a real Host.

## Slices

1. Test `pkg/host_rekey_runbook_test.go` (`TestRekeyRunbook_*`), two real
   barriers each initialised with its own root key:
   - (a) a Host on barrier A proposes values, takes `SyncRequestSnapshot`,
     proposes more, closes;
   - (b) `waldb.Reencrypt` from the A directories into new directories under
     barrier B, the snapshot function calling `ReencryptSnapshotFile`,
     returns count > 0 and no error; the A directories are byte-identical
     to before;
   - (c) after the swap, a Host on barrier B recovers the shard and every
     value (from the snapshot and from entries after it) reads back with
     `SyncRead`;
   - (d) opening the new WAL with barrier A fails; the original directories
     are unchanged.
2. Per divergence between the code and the docs: a failing test commit, then
   a fix commit in pkg/snapshot_reencrypt.go or pkg/logdb/waldb/reencrypt.go
   (or a doc correction in docs/seal-barrier/user.md when the code is right).
3. PR #883 review fix: ReencryptSnapshotFile reads the source snapshot.meta
   once through its snapshotFS (`TestReencryptSnapshotFile_CrashFSSourceMetaRestamped`),
   then crashFS fault tests for the restamp path: source meta read failure,
   destination meta write, sync and close failures, and a crash between the
   data rename and the directory fsync.
4. PR #883 review fix (P1): the restamp truncated snapshot.meta in place via
   writeReceivedSnapshotMetadata, which assumes an unpublished staging
   directory. Over a published pair a crash could pair the old snapshot.dat
   with the new record (a valid snapshot refused at recovery) or tear the
   record. Fix: refuse a destination snapshot.dat with fs.ErrExist when the
   source has a snapshot.meta; write the new record to a temp file and rename
   it over snapshot.meta. Tests: `_CrashFSExistingDestinationKept`,
   `_CrashFSMetaReplacedWhole` (crash on meta write, sync, rename).

## Out of scope

- Multi-replica re-key, re-sync from peers, `PurgeEpochsBefore` after the
  re-key, and any wire or on-disk format change.
