# #772: every Host method that takes a context returns promptly when it is cancelled

Objective: one test, `pkg/host_context_cancel_test.go`, that finds every exported
`*Host` method whose first argument is a `context.Context` by reflection and calls it
with a cancelled context, so a new method is covered by default.

Slices:
1. This plan.
2. `TestHostContextCancel`: for each method, (a) an already-cancelled context against
   a single-node shard with a leader, and (b) a context cancelled 50ms into a call
   against a three-member shard that cannot reach quorum. Each must return within 2s
   with an error matching `context.Canceled`, `ErrCanceled` (the documented library
   cancellation error) or, in (b) only, any error returned before the cancel fired.
   Arguments come from a per-type default, overridden by an explicit per-method
   table. A goroutine count check after a settle catches leaked waiters.
3. Per bug found: a failing test commit, then the fix in pkg/host.go or
   pkg/leaderexec.go.

4. Slice 2: a cancelled call returns an error matching both `ErrCanceled` and
   `context.Canceled`, an expired one both `ErrTimeout` and
   `context.DeadlineExceeded` (`mapContextError` wraps the context error; the
   `ctx.Done()` branches that return the bare library errors use it). The test
   requires both matches and adds an expired-deadline case; ExportSnapshot runs
   without a saved snapshot, so it must read its context first.

Out of scope: wire or on-disk formats.

## Review fix

The in-flight case accepted any result returned before the cancel, and its
no-quorum fixture made the blocking calls fail early (NotLeader, a rejected
NoOP session), so it never exercised their cancellation. It now runs on an
elected single-replica shard whose state machine Update blocks until released,
with valid arguments (a registered session for ProposeWithSession). Each
blocking method must still be pending at 50ms, is then cancelled, and must
return the cancellation error within the bound. Methods that cannot block are
named in a table with the reason and must return without a cancel.

## Review fix 2 (PR #784)

(a) Lint: rlockContext sat between Lookup's doc comment and Lookup, so revive
saw Lookup undocumented. rlockContext moves above Lookup's comment.

(b) rlockContext started a helper goroutine per contended read that stayed in
RLock until Update released the guard, so cancelled reads against a stalled
Update piled up goroutines. It becomes a TryRLock loop with a capped backoff
timer that returns ctx.Err() when ctx is done; TryRLock fails while a writer
waits, so it cannot starve Update. Test: hold readGuard.Lock, cancel 100
contended Lookups, goroutine count returns to baseline with the lock held.

(c) SyncRead returned the raw Lookup context error; wrap with
mapLocalReadError as QueryLocalNode does.

(d) SyncReadBuf called NALookupBuf (Background, plain RLock); use
NALookupBufContext(ctx, key) with mapLocalReadError.

(e) The in-flight case blocks Update before every call, so SyncRead and
SyncReadBuf only waited in ReadIndex. Add a lookup-stage case: ReadIndex
completes first, then an Update holds the guard during the lookup; cancel at
50ms, ErrCanceled within 2s, no leaked goroutine before release. The order
is made deterministic by an unexported hook, syncReadLookupHook (nil in
production), that runs between the applied read index and the lookup; the
test starts the blocking Update from it.
