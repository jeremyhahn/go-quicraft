# Plan: #902 — ReadIndex refused by the shard (Refs #744)

## Objective

Cover the documented `OnReadIndexDropped` contract (docs/multi-group-host/api.md,
Raft events table): when `Host.ReadIndex` cannot hand the read to the shard's
ReadIndex queue it returns `ErrSystemBusy`, fires `OnReadIndexDropped` with the
shard's `EventShardInfo`, and rolls back the pending read and pending-op count.

## Slices

1. `docs: plan for #902` — this file.
2. `test: a ReadIndex the shard cannot take returns ErrSystemBusy, fires
   OnReadIndexDropped and leaves nothing pending` — new
   pkg/host_readindex_dropped_test.go, `TestReadIndexDropped_*`:
   - single-replica transportless Host, listener records OnReadIndexDropped;
   - after the leader is elected, fill the engine node's ReadIndex queue with
     `DeliverReadIndex` until it refuses, then call `h.ReadIndex`, retrying
     until it fails or 5 s pass;
   - asserts: `errors.Is(err, ErrSystemBusy)`; nil RequestState; event fired
     with ShardID 1, ReplicaID 1; `pendingReads` holds no entry beyond those
     present before the call; `Drain` returns promptly (no leaked pending op).
3. Per divergence from the docs: a failing `test:` commit, then a `fix:`
   commit in pkg/host.go (or a doc correction if the code is right).

## Out of scope

- Any change to the ReadIndex batching, queue sizes or other events.
- Wire or on-disk formats.

# GitHub #902: concurrent SyncPropose across a leader change (PR #928)

The plan above predates the move to GitHub and covers another issue that had
the same number. This section covers PR #928's concurrent-propose tests
(pkg/concurrent_propose_test.go, pkg/concurrent_propose_leaderchange_test.go)
and the two P1 review findings against them.

## Finding P1-a: the replica checks only saw log replay

`concurrentProposeDrain` calls `restart`, which closes every host and then
clears `c.machines`. So `concurrentProposeCheck` and
`concurrentProposeSameCount` only saw fresh state machines rebuilt by log
replay. Replay applies each persisted entry once, which hides a duplicate
apply or a replica divergence that happened during the concurrent workload.

Fix: after every host's `Close` and before the machines are cleared,
`restart` saves each machine's snapshot in `c.preRestart`. The barrier key is
proposed after the restart, so it is not in those counts. First, `restart`
waits up to 10 s for the running replicas to agree, so a follower that is a
few entries behind is not reported as divergent. A real divergence never
settles, and the check then reports it. `concurrentProposeCheckPreRestart`
runs in all three tests right after the drain and asserts on the saved
counts:

- on a running replica, every acknowledged key applied exactly once;
- on a replica the test shut down (`c.closeHost`), each acknowledged key
  applied at most once;
- no key applied twice on any replica;
- no refused or unknown key applied;
- the same count per key on every running replica, and on a downed replica
  only keys the running replicas also hold.

The post-replay checks stay as a separate step.

## Finding P1-b: the held proposals were cancelled before they were collected

The leader-change test called `cancelHeld()` before it collected the held
`SyncPropose` results. Each held call then returned a MaybeApplied-wrapped
`ErrCanceled` whatever `OnLeaderUpdated` did, so the test still passed with
the leader-loss failure path (`failLeaderChangeRequests` with a
`*NotLeaderError` in pkg/host.go) deleted.

Fix: the held results are collected under the live 60 s test ctx, and each
one must satisfy `MaybeApplied(err) && errors.Is(err, ErrNotLeader)`. If a
call never returns, the test reports the stuck keys by name. `cancelHeld`
stays only as the deferred cleanup.

## Non-vacuity (temporary mutations, never committed)

- `recordingStateMachine.Update` applying `acked-00` twice: the pre-restart
  check fails in both leader-change tests.
- Both `failLeaderChangeRequests` calls in the `OnLeaderUpdated` paths of
  pkg/host.go skipped: the leader-change test fails with every held key
  (`gate`, `held-00`..`held-07`) reported as never returning.
