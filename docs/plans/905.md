# #905: a snapshot compacts the log

Refs #744 (v1.0.0 bar test gap).

## Objective

docs/multi-group-host/api.md says a snapshot lets the log drop entries
older than the snapshot index minus `CompactionOverhead`, that `LogRange`
and `LogReader` report the retained range, and that `QueryRaftLog`,
`RequestCompaction` fail with the documented errors. No test checks that a
snapshot moves the retained range. Add one.

## Slices

1. This plan.
2. pkg/host_log_compaction_test.go, on a single-voter transportless Host
   with a hashing state machine:
   - TestLogCompaction_SnapshotMovesRetainedRange (memory LogDB):
     (a) 200 proposals, record `StateMachineHash`, `SyncRequestSnapshot`
     with `CompactionOverhead: 10` overridden; wait until `LogRange`
     FirstIndex is above 1 and at most snapshot index - 10 + 1;
     (b) `LogReader(1).GetRange` reports the same FirstIndex;
     (c) `QueryRaftLog` [1, FirstIndex) fails with `logdb.ErrCompacted`,
     a reversed range with `ErrInvalidRange`, a range at or above
     FirstIndex returns entries;
     (d) `RequestCompaction(1, 1)` is nil, `RequestCompaction(1, 99)` is a
     `*ReplicaNotFoundError`;
     (e) `StateMachineHash` equals the recorded hash.
   - TestLogCompaction_RestartOnWALKeepsState (real WAL in t.TempDir):
     (f) after the snapshot and a restart the hash and applied index are
     unchanged and a new proposal succeeds. The state machine here saves
     and recovers its digest in the snapshot.
3. Per divergence between code and docs: a failing test commit, then a fix
   in pkg/host.go (or a doc fix in docs/multi-group-host/api.md where the
   code is right).

## Out of scope

Multi-replica compaction, snapshot transfer to followers, WAL segment GC
accounting, `RequestCompaction` on a paused shard (covered elsewhere).
