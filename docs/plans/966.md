# #966: seal-barrier persist and restart snippet as a compiled example

Refs #744 (v1.0.0 bar test gap).

## Objective

The "Minimal correct setup" block in docs/seal-barrier/user.md persists
`SealedRootKeyData` through `persistSealedState`, then on restart loads it
with `SetSealedRootKey` and calls `Unseal`. No build checks it, and
`ExampleBarrier` covers one process lifetime only. Add a compiled example
that runs the same lifecycle across two barriers and a JSON file.

## Slices

1. `docs: plan for #966` (this file).
2. `test:` pkg/seal/example_persist_test.go, package seal_test,
   `ExampleBarrier_SetSealedRootKey` with an `// Output:` block:
   - (a) `NewBarrier(DefaultBarrierConfig(1))` with a `StatePersister`
     that writes JSON to a temp file; `Initialize` with a
     `NewSoftwareStrategy` strategy; `SealedRootKeyData` written as JSON.
   - (b) a value is encrypted; the barrier is sealed.
   - (c) a new barrier reads the JSON, `SetSealedRootKey`, `Unseal` with a
     strategy from the same passphrase; `Decrypt` returns the value.
   - (d) `Unseal` with a strategy from a different passphrase fails with
     a `*UnsealError` (docs/seal-barrier/api.md, Errors (`Unseal`)) and
     the barrier stays sealed.
   Every barrier is sealed on every return path. The guide block points
   at the example.
3. Per divergence between code and docs: a failing `test:` commit, then a
   `fix:` commit in pkg/seal/barrier.go; a wrong doc is corrected in
   docs/seal-barrier/user.md instead.

## Out of scope

- The Host wiring in the guide block (`quicraft.NewHost`), FIPS, and
