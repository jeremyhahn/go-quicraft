# #786: SyncRead after a leader transfer observes acknowledged writes

Objective: prove that `Host.SyncRead` never returns state older than an
acknowledged write once leadership moves with `RequestLeaderTransfer`, on the
old leader, the new leader and a follower.

Existing coverage: `test/integration/linearizability` checks reads across
failover, restart and membership change, but no case there calls
`RequestLeaderTransfer`. This row adds only the transfer case.

Slices:
1. `pkg/syncread_leader_transfer_test.go`: a three-host shard over the real
   transport (the `nextWireCluster` helpers in `pkg/wireswitch_nextwire_test.go`)
   with a counter state machine. 20 rounds of: propose an increment on the
   leader and wait for the ack, transfer leadership to another replica, then
   SyncRead on the old leader, the new leader and the follower, each with its
   own deadline, asserting the value is at least the acknowledged count.
2. If a read is stale: a failing test commit, then the fix in
   `pkg/internal/raft/` or `pkg/host.go`.

Verify note: the intermittent pkg coverage-shard FAIL reproduces (GOMAXPROCS=2, -race -count=4 ./pkg/) only in tests outside this row (pkg/host_drain_test.go:174, pkg/session_retry_leader_change_test.go:272); this row's tests pass -race -count=30.

Out of scope: wire or on-disk format changes; other read paths (LeaseRead,
StaleRead).
