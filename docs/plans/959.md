# Plan: #959 — snapshot CompactionOverhead override

Refs #744 (v1.0.0 bar test gap).

## Objective

Prove `SnapshotOption.CompactionOverhead` / `OverrideCompactionOverhead`
behave as documented in `pkg/snapshot_option.go`: with the override the
option's value replaces the shard's `Config.CompactionOverhead` for that
snapshot's log compaction, and without it the shard's value applies.

## Slices

1. `pkg/snapshot_option_overhead_test.go` (package quicraft), one test
   `TestSnapshotOptionOverhead`, on a single-replica Host without transport,
   with an on-disk LogDB, a KV state machine, the shard's
   `CompactionOverhead` = K = 10 and automatic snapshots off:
   - (a) after 60 proposals, the override with C = 3 snapshots at S and
     LogRange.FirstIndex becomes S-C+1 (C entries up to S retained);
   - (b) 40 more proposals, no override: FirstIndex becomes S-K+1;
   - (c) 20 more proposals, override with C = 0: FirstIndex becomes S+1;
   - (d) 40 more proposals, CompactionOverhead 2 without the override:
     ignored, FirstIndex becomes S-K+1;
   - (e) after each case the Host is closed and restarted on the same
     directories: the state machine hash matches and LogRange.FirstIndex
     is unchanged (LastIndex may grow by the new term's entry).
   All waits poll a condition under a bounded deadline.
2. Per divergence from the docs: a failing test commit, then a fix commit
   in `pkg/host.go` or `pkg/snapshot_option.go` (or a doc-comment fix when
   the code is right). A fix outside those files is reported, not made.

## Out of scope

Multi-replica catch-up behaviour, exported snapshots, automatic snapshots,
any change to wire or on-disk formats.
