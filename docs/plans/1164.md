# #1164: run the linearizability and partition suites with WAL fsync on

## Objective

Every cluster harness sets `NoSyncWAL: true`, so no linearizability or
partition run exercises the fsync-before-ack path production uses. Add a
WAL-sync mode to the linearizability and e2e harnesses and run it once per CI
full-tier Integration run.

## Slices

1. Harness (test/integration/{linearizability,e2e,raft,host}/helpers_test.go)
   - `QUICRAFT_IT_WAL_SYNC=1` selects WAL-sync mode (`harnessWALSync(getenv)`).
     linearizability and e2e: `testHostConfig` sets `NoSyncWAL = !walSync`.
   - Sync mode raises the host tick (RTTMillisecond) from 50ms to 500ms, so
     the shortest election timeout (DefaultElectionRTT = 10 ticks) is 5s,
     above the measured 2.5-4.6s fdatasync stalls. Raising the tick, not the
     shard's ElectionRTT, covers the shard configs the suites build outside
     testShardConfig. electionRound / leaderElectionTimeout / failoverTimeout
     follow the mode's tick. Neither helper has a snapshot wait timeout of
     its own; the snapshot waits use defaultTimeout or the election budgets.
   - Tests: `TestHarness_WALSyncMode` per package replaces
     the old NoSyncWAL pin tests (and raft's NoSyncWAL check):
     linearizability/e2e give NoSyncWAL=true unset, false with `=1`; raft and
     host give true either way. `TestBudgetsDescribeTheClusterTheyBudgetFor`
     pins the budgets to the builders in both modes and checks the sync
     mode's shortest election timeout exceeds the stall ceiling. Host's
     `TestHarness_RestartConfigKeepsWALSync` is kept.
2. Makefile: `integration-test-walsync` runs, in the integration image with
   `-e QUICRAFT_IT_WAL_SYNC=1`, the linearizability package and the e2e
   `-run 'Partition'` cases that are in IT_PKGS, nothing when neither is.
   `integration-test` runs the same after the main IT_CMD run succeeds,
   inside its status/teardown handling, so ci.yml is unchanged.

3. Review fix (PR #1171 P1): the 500ms tick made the failover tests'
   client windows end before recovery was exercised. In
   linearizability_test.go, LeaderFailover and ElectionSafety size their
   post-kill run, restart delay and floors in electionRound (1s by default,
   so those schedules do not change; 10s in WAL-sync mode).
   `requireServedSince` fails the test unless at least one write and one
   read were acknowledged after the new leader's election (and, in
   ElectionSafety, also after the old leader rejoined).

## Out of scope

- The raft and host suites stay NoSyncWAL.
- The quicraft_netfault NetPartition cases run in the netfault job.
- .github/workflows/ci.yml is not edited.
