# #843: session expiry through the Host

## Objective

docs/client-sessions/api.md and docs/client-sessions/user.md say session expiry
counts applied entries: a session with no activity for `SessionExpiryEntries`
applied entries is reclaimed, a later `SyncProposeWithSession` returns
`*SessionExpiredError` (`errors.Is` `ErrSessionExpired`), `CloseSession` of it
completes with `*SessionExpiredError`, an active session never expires,
`config.SessionExpiryDisabled` turns expiry off, and an idle shard expires
nothing. No test drives a real expiry through a Host. This row adds one.

## Slices

1. `docs: plan for #843` (this file).
2. `test:` pkg/host_session_expiry_test.go, single-replica in-memory Hosts with
   `SessionExpiryEntries = 100` (the configured floor):
   - (a) an idle session across 250 applied `SyncPropose` entries gets
     `*SessionExpiredError` from `SyncProposeWithSession` and from the
     completed `CloseSession`;
   - (b) a session proposing once per 50 entries over the same span never
     expires;
   - (c) with `SessionExpiryDisabled` an idle session survives the same
     traffic;
   - (d) with no traffic a session still proposes after a 2 s wait;
   - (e) with `MaxSessionsPerOwner = 1`, an expired owner session frees the
     slot so `NewSessionWithOwner` for that owner succeeds.
3. Per divergence from the docs: a failing `test:` commit, then a `fix:`
   commit in pkg/internal/rsm/statemachine.go (or a doc fix in
   docs/client-sessions/user.md when the code is right).

## Out of scope

- Multi-replica expiry, snapshot/restore of expired state, wire or on-disk
  format changes.
