# Plan: #1175, health reports not-ready when a started shard has no leader

## Objective

`Host.HealthCheck()` returns `"ok"` on a host whose shard cannot elect a
leader (for example a single node started with a peer list it cannot
reach), so no write can commit while health says the host is fine.
HealthCheck must report `"not-ready"` and name the shard once a started
shard has had no known leader for longer than its election timeout
(`ElectionRTT * RTTMillisecond`), without flapping during a normal
election.

## Slices (one PR, commits in order)

1. Regression test, `pkg/host_healthcheck_states_test.go`
   (`TestHealthCheck_NotReadyWhenLeaderlessPastElectionTimeout`). Fails on
   the current code:
   - a single-node host started with three unreachable peers reports
     `"not-ready"` after the election timeout and lists the shard in
     `not_ready_shards`;
   - a healthy single-member shard reports `"ok"` with no list;
   - a shard leaderless for less than its election timeout is still
     `"ok"` (ElectionRTT set large so the window is deterministic).
2. Fix:
   - `nodeState.leaderlessSince` (`atomic.Int64`, unix nanoseconds, 0 while
     a leader is known): set at shard start, kept at its first value while
     the shard stays leaderless, cleared by `updateNodeLeader` when a
     leader is published. No lock on the hot path.
   - `HealthStatus.NotReadyShards []uint64` (`not_ready_shards`,
     omitempty), sorted.
   - `HealthCheck`: sealed > unhealthy (no shards) > degraded (any
     ShardError, unchanged) > not-ready (any unpaused shard with
     LeaderID 0 for longer than its election timeout) > ok. Paused shards
     are excluded: pausing is an operator action already reported by
     `Paused`.
3. Docs: `docs/observability/api.md`, `docs/observability/user.md`
   describe the new status, the field and the timeout rule;
   `CHANGELOG.md` Unreleased line.
4. Codex review round 1 (two P1s): test commit, then fix, then docs.
   - The window is `3 * ElectionRTT * RTTMillisecond`, not the nominal
     timeout: raft randomizes the timeout in `[E, 2E)` ticks and the
     campaign needs one more timeout to win
     (`TestHealthCheck_LeaderlessGraceCoversRandomizedElection`,
     `TestHealthCheck_HealthyStartupNeverNotReady`).
   - `ResumeShard` restarts the window of a leaderless shard it resumes
     (`TestHealthCheck_ResumeRestartsElectionWindow`).
5. Codex review round 2 (two P1s): test commit, then fix.
   - Tests: `Host.clock` (a `leaderlessClock` with wall and monotonic
     readings, nil = system clock) lets a test step the wall clock alone
     (`TestHealthCheck_LeaderlessWindowIgnoresWallClockSteps`, fails on
     the wall-clock window); a leader lost long after startup gets a
     fresh window, repeated leaderless updates keep it, a new leader
     clears it (`TestHealthCheck_LeaderLossAfterElectionOpensFreshWindow`,
     a coverage regression: fails if `updateNodeLeader` stops updating
     `leaderlessSince`).
   - Fix: `leaderlessSince` stores monotonic nanoseconds since the
     process-local `monoOrigin`; the 3x window and the resume reset stay.

## Out of scope

- Detecting a leader that vanished without the engine publishing a
  leader change (leaderID stays non-zero).
- Changing the per-shard `ShardHealth` values or the degraded rule.
- Any HTTP/CLI surface beyond the documented JSON field.
