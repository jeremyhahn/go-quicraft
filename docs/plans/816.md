# #816: SyncRemoveData deletes a stopped replica's data and refuses a running one

Objective: prove on an in-process three-replica shard (real WAL, mTLS) that
`RemoveData`/`SyncRemoveData` refuse a running replica and remove a stopped one.

Slice 1 (pkg/replica_remove_data_test.go):
- propose entries; `SyncRemoveData` and `RemoveData` on a running follower
  return an error matching `ErrShardNotStopped` (errors.Is); its LogDB state
  and snapshot directory are unchanged.
- `StopReplica` the follower, `SyncRemoveData` it: LogDB holds no state,
  bootstrap or entries for it and reports it removed.
- RemoveData retires the replica ID (documented, host.go RemoveData doc): a
  restart under the same config is refused with `ErrReplicaRetired`; the
  replica rejoins under a new ID (delete 3, add 4) and its `StateMachineHash`
  reaches the leader's.
- the other two replicas accept proposals throughout.

A removal bug found here gets a failing test commit, then a fix in pkg/host.go.
Out of scope: wire or on-disk format changes; other packages.

## Review fix

`make coverage` failed at replica_remove_data_test.go:253: the snapshot
directory `<root>/shard-N/shard-N/replica-M` survives removal. The nesting is
the real layout (shardSnapshotBaseDir + engine.ReplicaSnapshotDir, as
StartShard creates it) and the test already uses those helpers. The defect:
RemoveData removed only LogDB data and no snapshot path at all. Fix in
pkg/host.go: RemoveData resolves the root from the bootstrap record's DataDir
and removes the replica's snapshot directory; a test covers a DataDir shard.

## Review fix (round 3)

Two P1s in RemoveData. (1) StartShard saved no bootstrap record for a join, so
a joined replica with a custom DataDir was removed under NodeHostDir and its
snapshots stayed: StartShard now records `{Join: true, Type, DataDir}` (no
Addresses) for a join too; resolveImportDataDir and waldb reencrypt read only
DataDir or copy the record, so a Join record is safe. (2) RemoveNodeData ran
before the snapshot RemoveAll, so a failed RemoveAll lost the record and a retry
removed the wrong tree: the snapshot directory goes first. Tests: a joined
DataDir replica's snapshots are removed; a failed RemoveAll is retried.

## Review fix (round 4)

Two P1s. (1) Deleting the snapshot directory before retirement lost a compacted
log's snapshot when retirement failed: RemoveData now writes a durable,
host-local intent `<NodeHostDir>/remove-data/shard-S-replica-R` naming snapDir,
retires the replica, removes snapDir, then the intent; a retry finishes from the
intent. (2) Without a bootstrap record the layout is taken from a pending intent,
else the LogDB snapshot record's Filepath (refused with
RemoveDataLayoutUnknownError when it is not a replica layout), else NodeHostDir.
Tests: failed retirement keeps the snapshot; imported and pre-record joins.

## Review fix (round 5)

(1) The unknown-layout refusal is the unexported `removeDataLayoutUnknownError`
in pkg/host.go, matching `ErrInvalidOperation` under errors.Is; pkg/errors.go
has no diff against main. (2) A removal intent is durable only once
`syncRemoveDataIntentDir` has synced `remove-data` and NodeHostDir; RemoveData
runs it after every intent write and before retiring from a pending intent.
Tests: the refusal's fields via errors.As; a failed intent directory sync does
not retire, and a retry (rewrite and pending) syncs both before retiring.

## Scope

Edited files: pkg/host.go, pkg/replica_remove_data_test.go, docs/plans/816.md,
and pkg/host_test.go: TestStartShard_Join_NoBootstrap and
TestStartShard_LosesRaceWithClose change because a join now records its
DataDir in a bootstrap record (round 3): the first asserted no record for a
join and now checks `{Join: true, no Addresses, DataDir}`; the second relied on
a join writing no record and now expects the save after Close to fail.
