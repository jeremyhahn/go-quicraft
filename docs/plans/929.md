# Plan for #929: SetQueryTimeout bounds ReadLocalNode and NAReadLocalNode

Refs #744 (v1.0.0 bar test gap).

## Objective

contrib/dragonboat/README.md says `ReadLocalNode` and `NAReadLocalNode` are
bounded by `QueryTimeout` (set by `SetQueryTimeout`; zero or negative means
no deadline). `readLocalNode` passes a context with that deadline to
`Host.QueryLocalNode`, but the dragonboat state machine adapters discard the
context and call the user's context-free `Lookup`/`NALookup`, so a blocking
lookup is not bounded. Prove the documented behaviour with tests, and fix
the code where it diverges.

## Slices, in order

1. This plan.
2. Test commit: contrib/dragonboat/nodehost_query_timeout_test.go with a
   test-local state machine whose `Lookup` (and, for the IExtended variant,
   `NALookup`) blocks on a channel the test controls:
   - (a) `SetQueryTimeout(200ms)`, completed `ReadIndex`: `ReadLocalNode`
     returns within 2 s with `ErrTimeout` while `Lookup` is still blocked;
   - (b) the same for `NAReadLocalNode` with a blocking `NALookup`;
   - (c) once released, the next `ReadLocalNode` returns the stored value;
   - (d) after `SetQueryTimeout(0)` and `SetQueryTimeout(-1)`,
     `QueryTimeout()` is 0 and `ReadLocalNode` waits for a `Lookup`
     released after 300 ms and returns its value.
   Expected to fail on (a) and (b) against main.
3. Fix commit in contrib/dragonboat/nodehost.go: when a query deadline is
   set, `readLocalNode` runs the local query in a goroutine and returns
   `ErrTimeout` when the deadline passes first; the blocked lookup finishes
   in the background and its result is discarded.

## Out of scope

- Making the dragonboat adapters' user `Lookup` context-aware (the
  dragonboat `IStateMachine` interface has no context).
- `SyncRead` / `StaleRead` deadlines, which are already caller-bounded.
- Any wire or on-disk format change.
