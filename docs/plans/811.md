# #811: RequestLeaderTransfer moves leadership and keeps every write

Objective: prove `Host.RequestLeaderTransfer` hands leadership to the named
follower under write load, and that no acknowledged write is lost.

Slice 1 (this PR), pkg/leader_transfer_test.go:
- Three in-process hosts (mTLS QUIC on loopback) run one KV shard.
- 8 goroutines propose distinct Puts through whichever replica leads.
- The test transfers leadership to each follower in turn; each time
  `LeaderIDAndTerm` must report the target at a higher term within 10
  election timeouts.
- Every failed proposal must match `ErrTransferInProgress`, `ErrNotLeader`,
  `ErrDropped` or `ErrTimeout` with errors.Is.
- After load stops, every replica reaches the same applied index, every
  acknowledged key is present on every replica, and `StateMachineHash`
  agrees across replicas.
- A found bug gets a failing test commit, then a fix in pkg/host.go.

Out of scope: wire or on-disk format changes, transfer target selection.

## Review fix

- A transfer counts only when it was requested: before each request the
  test establishes the agreed leader and term, picks a follower of that
  leader as the target, requires `RequestLeaderTransfer` to succeed, then
  requires the target to lead at a higher term.
- Fixed sleeps give way to progress barriers: before the first transfer and
  after each one, every proposer must have an acknowledged write in the
  current term. After the last transfer, acknowledged writes from every
  earlier term must be present on every replica.
