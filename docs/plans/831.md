# #831: a confirmed ReadIndex can complete a recycled RequestState

## Objective

Under -race, confirmReadyReads (pkg/host.go, the `complete` closure) read
`pr.rs.createdAt` of a RequestState that newRequestState, called from
Host.ReadIndex, was initialising for a new request. The pendingReads entry
outlived its RequestState: the object had been returned to the pool while
the entry still held it.

Every pendingReads removal site deletes under pendingReadsMu and pairs one
releaseRef with the entry's acquireRef, so the map accounting is balanced.
The fault is in the recycle decision (pkg/requeststate.go):

1. A completion's releaseRef drops `outstanding` to 0 while the caller has
   not released yet, then is preempted before tryRecycle.
2. The caller's Release recycles the object (its own releaseRef also sees 0
   with `released` set); a new ReadIndex takes it from the pool.
3. The stale tryRecycle resumes: it loads `released` (still true) before
   newRequestState resets it, then loads `outstanding` (0) and wins the
   `recycled` CAS after the reset, and puts the live object in the pool a
   second time. The next newRequestState hands the same object to another
   request while the first request's pendingReads entry still points at it.

tryRecycle's three loads are not one atomic decision, so two goroutines can
both see "last reference" for one incarnation.

## Slices

1. Test (pkg/readindex_recycle_test.go): many workers drive the read
   lifecycle on one pool (newRequestState, acquireRef, a completer's
   releaseRef racing the caller's Release) and check that each request still
   owns its object (its key unchanged) until it releases it. A double
   pool.Put shows as two live requests sharing one object. It fails on
   f01d610b.
2. Fix (pkg/requeststate.go): count the caller's reference with the
   pending-map references in one counter (`holders`): newRequestState starts
   it at 1, acquireRef/tryAcquireRef add 1, releaseRef and the first Release
   subtract 1, and only the goroutine that takes it to 0 recycles. A counter
   that has reached 0 is never raised again, so exactly one goroutine
   recycles each incarnation. `outstanding` keeps its meaning (pending-map
   references) for the existing tests. A second Release no longer touches
   the counters.

## Verify fix

The fix stands unchanged. Two older tests built a "zero references" state
with newRequestState alone, which under `holders` is one live holder.
Rewrite them to reach zero holders through acquireRef, Release and
releaseRef: TestTryAcquireRef_FailsAtZero (pkg/requeststate_test.go) and
TestHostEngineCallback_OnCommitted_SkipsUnreferencedProposal
(pkg/host_test.go, counting tryRecycle entries via testHookTryRecycle so a
missing guard shows as a second recycle). No production change.

## Out of scope

- Wire and on-disk formats, the pendingReads map layout, alias handling.
- Pending proposals and snapshots: they share the fix through releaseRef.

## Review fix

TestPendingReadRecycleUnderContention waited only for its workers, not for
the completer goroutines each worker starts. A late completer's releaseRef
runs tryRecycle, which reads testHookTryRecycle after the test returned
while a later TestPendingReadNeverCompletesRecycledRequestState writes it:
a data race under the repeated -race run. Track every completer in a second
sync.WaitGroup and wait on it after the workers, before the failures check.
No production change.
