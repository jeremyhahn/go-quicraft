# #915: a snapshot over MaxSnapshotSize fails cleanly

Tracked under #744 (v1.0.0 bar test gap).

## Objective

docs/snapshots/user.md, docs/snapshots/engineering.md and
docs/multi-group-host/user.md say a snapshot whose state machine output
(after compression, before sealing) exceeds `Config.MaxSnapshotSize` is
discarded with `*SnapshotTooLargeError` (ShardID, MaxSize; matches
`ErrSnapshotTooLarge`). The engine check and the Host translation are only
tested in isolation. This row proves the documented behaviour end to end on
a Host with a real WAL.

## Slices

1. `docs: plan for #915` (this file).
2. `test:` pkg/host_snapshot_size_limit_test.go, one test
   `TestSnapshotSizeLimit_*` on a transportless Host (real WAL, no
   encryption) with a state machine whose snapshot grows with the data and
   a recording EventListener:
   - (a) large limit: propose 10 entries, `SyncRequestSnapshot` → S1;
   - (b) restart with a limit below the next snapshot, propose 200 x 1 KiB,
     `SyncRequestSnapshot` fails with `*SnapshotTooLargeError{ShardID: 1,
     MaxSize: limit}` and `errors.Is(err, ErrSnapshotTooLarge)`;
   - (c) `OnShardFailed` never fired, `OnSnapshotCreated` only for S1,
     `LogRange().FirstIndex` did not move, no snapshot directory newer than
     S1 remains;
   - (d) a further `SyncPropose` succeeds and the state machine digest
     equals a replay of every acknowledged proposal;
   - (e) restart with MaxSnapshotSize 0 (default): `SyncRequestSnapshot`
     succeeds at an index past S1.
3. Per divergence from the docs: a failing `test:` commit, then a `fix:`
   commit in pkg/host.go or pkg/internal/engine/snapshot_pool.go (or a doc
   correction in docs/snapshots/user.md when the code is right).

## Out of scope

- Encrypted (barrier) snapshots; the sealed-size measurement is covered by
  engine unit tests.
- Snapshot transfer to followers and import paths.
- Any wire or on-disk format change.
