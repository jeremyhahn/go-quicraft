# Plan: kill-based restart cases for the WAL (#1165)

## Objective

Every integration restart today closes the old host with `Close` in the same
process, which flushes and syncs the WAL first. Nothing proves that an entry
acknowledged to a client survives an abrupt process kill. This row adds
integration cases that run a node in a child process with WAL fsync on,
SIGKILL it, restart it on the same directories and check every acknowledged
entry is still there and the cluster stays linearizable.

## Slices

One slice, one new file: `test/integration/linearizability/kill_restart_test.go`.
The linearizability package is in the integration shards, so the cases run in
the CI full tier without Makefile or ci.yml changes.

- `TestKillRestart_Child`: child entry point, skipped unless
  `QUICRAFT_KILLRESTART_CHILD=1`. Reads a JSON spec the parent wrote (dirs,
  fixed address from `netport.MustReserveUDP`, mTLS leaf files from
  `testpki.LeafFiles`, members, mode), opens one Host with `NoSyncWAL=false`,
  starts the shard and never calls `Close`. Each acknowledged proposal is
  appended to an ack file that is fsynced before the next step.
- `TestKillRestart_AfterAcks`: single replica, N sequential acks, kill with
  nothing in flight, reopen in-process, every acked key reads back.
- `TestKillRestart_MidBatch`: single replica, several concurrent proposers,
  kill while proposals are in flight; acked keys present, in-flight keys
  present or absent, never corrupt.
- `TestKillRestart_DuringSnapshot`: single replica, small `SnapshotEntries`,
  a state machine whose second `SaveSnapshot` writes a marker and blocks; the
  parent kills on the marker.
- `TestKillRestart_3Node_Linearizable`: two in-process hosts plus the third
  replica in a child; clients record with `opRecorder`; the child is killed
  (as leader when `RequestLeaderTransfer` moves leadership there, else as a
  follower) under load and restarted as a new child; `checkLinearizability`
  passes and the restarted replica's state machine matches the survivors.
  The shard config uses an ElectionRTT sized for real fdatasync stalls.

Every case checks the child exited by signal (`ExitCode() == -1`, SIGKILL)
and logs the number of acked entries checked after restart.

## Out of scope

- Power-loss (page cache loss) simulation: SIGKILL keeps the page cache, so
  these cases prove the engine acks only what it has written and fsynced,
  and that recovery replays it; they do not drop unsynced pages.
- Changes to helpers_test.go (another lane owns it), the Makefile or ci.yml.

## Review fix (PR #1172, two P1)

- Mid-batch kill boundary: `kill` first sends SIGUSR1. The child freezes its
  ack record (a proposal returning after the freeze is never recorded as
  acknowledged), waits until at least one submitted proposal has not
  returned, and writes `pre-kill in-flight N violations M`. The proposers keep
  submitting fresh keys, so the WAL stays busy until the parent SIGKILLs on
  that line. The mid-batch case fails unless N > 0 and logs N.
- Apply-order violations: the child polls helpers_test.go's violation sink
  every 2ms (and once more at the pre-kill freeze), writes each violation to
  the ack file and exits non-zero at once; the parent fails on a non-signal
  exit, on any `violation` line and on a non-zero M. Checked by a scratch run
  that injected one violation: AfterAcks and MidBatch both failed.
