# #782: stopping a shard mid-snapshot leaves no partial snapshot

Objective: prove at the Host level that a shard stopped (or a Host closed) while
its state machine is inside `SaveSnapshot` leaves no staging directory or
scratch file under the snapshot directory, and restarts cleanly on the same
directories with the state the applied entries produce.

Existing coverage: `pkg/internal/engine/incarnation_fence_test.go:709`
(`TestSnapshotPool_SaveIsFencedByUnload`) proves the pool-level fence on a bare
node; it does not stop through the Host, reopen the WAL, or check the state.

Slice (one commit): `pkg/snapshot_stop_midsave_test.go`, `TestMidSave*`:
- a hashing state machine whose `SaveSnapshot` blocks on a release channel;
- case 1: `StopShard` during the save, release, `StartShard` on the same Host;
- case 2: `Host.Close` during the save, release, `NewHost` on the same dirs;
- each asserts no `.save-*` stage or snapshot scratch temp remains, the shard
  serves a read, its hash equals the hash of the proposed entries, and a fresh
  snapshot then succeeds. Every wait has its own deadline.

If a case fails: a failing-test commit, then the fix under `pkg/internal/` or
`pkg/host.go`. Out of scope: format versions, transport, encryption.

## Slice 2

Decision: a race, not a leak. A stopped shard's request completes before its
pool worker's save returns; the deferred `os.RemoveAll(stageDir)` in
`saveSnapshotCompacting` runs only when that worker returns, while the Host
still runs. The pre-restart check polls with its own 5 s deadline and passes
before `StartShard` (so not by the sweep); the strict check stays after the
restart. No `snapshot_pool.go` change. The doubled `shard-1/shard-1` segment
is the layout: `shardSnapshotBaseDir` (`snapshots/shard-N`) is the pool's
base, and `snapshotSaveDir` appends `shard-N/replica-N/snapshot-<index>`.

## Review fix

P1-1: the save is released only after its stopper closes. SaveSnapshot
closes a gate channel `stopperClosed` (once) when its stopper closes, still
ignoring it for its own return; stopDuringSave waits for that (midSaveStep
deadline) before releasing, replacing the 200 ms timer. If StopShard or
Host.Close never closes the stopper, that is a finding, not a fix.
P1-2: `releaseSave()` (sync.Once) is registered as a t.Cleanup in
newMidSaveFixture, and every host cleanup goes through one helper that
releases the gate and bounds Close by midSaveStep.

## Review fix (round 2)

Clean tree: the go.sum change was test-run noise, restored and not committed.
The coverage failure in transport TestSendBatch_DirectWriteErrorViaConnectionClose
(send_test.go:1001, 10 s connection-close wait) is outside this PR; a rerun of
`-count=20` passed 20/20 in 100 s, so it is load-dependent. No Go code changed.
