# #1161: code-review workflow template v5.10.11 → v5.11.3

`.github/workflows/code-review.yml` is the handbook's
`software/templates/github-actions/code-review.yml` (handbook main `dc8643d`,
after `93c1eae2`), with this repository's CUSTOMIZE values spliced back in by
marker. Line 1 reads `# code-review-template: v5.11.3`.

## Diff against the template outside the CUSTOMIZE blocks

Empty. The copy is byte-identical to the template (`cmp` reports no
difference), because this repository's values at the template's CUSTOMIZE
points are the template's defaults:

| CUSTOMIZE point | This repository (base `64ee78e9`) | Template v5.11.3 |
|---|---|---|
| `COORDINATOR_TURNS` (workflow env) | `3` | `3` |

| `vars.OLLAMA_URL` | repository variable, not in the file | same |

## What the copy drops: the repo-local ruling-443 skip guard

The v5.10.11 copy carried two `# CUSTOMIZE (per repository …)` …
`# End of CUSTOMIZE.` blocks (`PROTECTED`, `CI_FILE`, `GATE_JOB`). They were not
template blocks: they are the head of the `GUARD_PY` heredoc in the repo-local
"Owner ruling 443" scope step (#720, #721: a workflow-only PR gets no review
when InfoSec's guard Y-1 to Y-8, Y-10 passes), once in the codex job and once in
the opencode job, plus the `steps.scope.outputs.skip != 'true'` conditions that
step added to later steps. The handbook template has never carried that step.

Template v5.11.0/v5.11.1 (ruling 589) replace it: the required
`Code Review (codex)` check is a `gate` job that passes on a Codex approval of
the head or on a change wholly inside `NO_REVIEW_PATHS` (`docs/`, `*.md`,
`.github/`, `.gitea/`, `changelog.d/`). A workflow-only PR therefore still
needs no review, but the InfoSec Y-checks on such a PR (protected workflow
stems, the CI gate's `needs` list) no longer run. Keeping the two blocks would
mean keeping the whole ruling-443 step, and the diff against the template would
not be empty, so this copy follows the template.

The splice script asserts the mismatch before it writes: the template has 0
marker blocks, the repository 2, and each of the repository's blocks is the
head of a `GUARD_PY` heredoc inside the ruling-443 step, which the template
does not contain. Each single-line CUSTOMIZE point occurs once in each file
(`NO_REVIEW_PATHS` occurs only in the template).

## Local divergence from template v5.11.3

PR #1162's review raised two P1 security findings against the template's new
`gate` job, lane-verify's pre-push review a third against the fix of the
second, the second review round two more against those fixes (items 4
and 5), lane-verify's pre-push review of item 4 a sixth, and its pre-push
review of item 6 three more (items 7 to 9), and its pre-push review of
items 7 to 9 two more (items 10 and 11), and the third review round one
more against item 11 (item 12). All are fixed here, each edit marked `# LOCAL (security):` with the
finding's title, for upstreaming to the template:

1. **Exclude the signing trust registry from the no-review exemption.** The
   blanket `.github/` exemption covered `.github/allowed_signers`, which the
   Signatures job in `ci.yml` trusts (from the base commit, so an unreviewed
   addition is trusted for every later PR). `REVIEW_REQUIRED_PATHS` lists the
   paths that are never exempt: any `allowed_signers` under `.github/`, and
   `.github/workflows/` and `.gitea/workflows/` (the removed ruling-443 scope
   guard checked the workflow stems; the gate's own definition must not change
   unreviewed). `allowed_signers` is the only `.github/` trust file `ci.yml`
   reads.
2. **Preserve the live-base guard in the new required gate.** The gate fails
   when the `review` job ended `failure` with its guard's `skip=retargeted` (a
   new `skip` job output), and reads the live PR: its base ref and head sha
   must equal the event's `BASE_REF` and `EVENT_SHA` (item 5 dropped the base
   sha from this comparison).
3. **The no-review exit bypasses the live-base guard** (lane-verify's
   pre-push review of item 2). The no-review change is classified against the
   event's `BASE_SHA`, and a retarget creates no new run (`edited` is not a
   trigger, and is not added), so item 2's checks are one `live_base_guard`
   function, run before the exemption is granted and again after the wait for
   in-flight reviews, before the verdict is read.
4. **Preserve failed re-reviews in the required gate.** An effort/model label
   on an approved code PR requests another review (the guard's `again`
   path); if that review job ends `failure` or `cancelled`, the gate fails for
   a non-exempt change before any older approval of the head is read. A
   `skipped` review job (no review requested) still falls through to the
   approval lookup, and the review job's benign guard exits (`closed`,
   `stale`, `unrequested`, `claimed`, `reviewed`, `label`) end `success`.
5. **Allow ordinary base-branch advancement without failing the gate.** The
   live PR's `base.sha` follows the target branch tip, so a merge into the
   base branch while the gate waits is not a retarget. `live_base_guard`
   compares only the live base ref and head with the event's; a different
   base ref is a retarget and fails. `BASE_SHA` stays the immutable pin of
   the diff the change is classified against.
6. **Preserve failed re-reviews across subsequent workflow runs**
   (lane-verify's pre-push review of item 4). Item 4 reads only this run's
   review job, so an unrelated label after a failed re-review started a run
   whose review job was skipped and the older approval passed. After the twin
   wait and the second `live_base_guard`, on GitHub, the gate reads the
   submission time of the reviewer's latest standing verdict on the head; if
   it is an approval, it reads every `Codex review` job of this workflow's
   runs for this PR on the head (item 9) and fails when any completed one
   concluded `failure`, `cancelled` or `timed_out` after that approval was
   submitted. Every such job counts, not only the latest non-skipped one: a
   later benign guard exit (`skip=reviewed`) ends `success` without
   reviewing. A new approval submitted after the failed run clears it. On
   Gitea the check is not made (Gitea is retired for this repository).
7. **Bind reused approvals to the change reviewed against the target base.**
   An approval of the head into base A passed after a retarget to B (an
   unrelated label then skips the review job), though B...H may hold
   unreviewed code. The verdict marker already carries `patch=<patch-id>`,
   the review key (`git patch-id --verbatim` of the merge-base-to-head
   diff). On GitHub the gate reads the diff `$BASE_SHA...$EVENT_SHA` of its
   event (compare API, `Accept: application/vnd.github.diff`), computes the
   same patch id, and fails unless the latest standing approval's marker
   carries it. The review job's already-approved path reuses the approval
   (`skip=reviewed`) only under the same rule, else codex reviews again. A
   diff GitHub will not serve (over its size limit) or an approval marker
   with no `patch=` fails the gate: no base can be established for it.
8. **Grant the gate token permission to read check runs.** The history of
   item 6 read `/commits/$EVENT_SHA/check-runs`, which needs `checks: read`
   the gate's permissions block does not grant. It is now read through the
   Actions API the gate already may read (`actions: read`):
   `/actions/workflows/$wf/runs?head_sha=$EVENT_SHA` (`$wf` is this run's
   workflow, read by the twin wait), paged, then
   `/actions/runs/<id>/jobs?filter=all` (every attempt), paged. The
   permissions block is unchanged.
9. **Scope historical failed review jobs to the same pull request.** The
   check-runs endpoint aggregated every PR's jobs on the head and any job
   named `Codex review`. Only this workflow's runs count (the runs list is
   per workflow), and of those only runs whose `pull_requests` holds
   `PR_NUM` or whose run-name is this PR's (`Code Review: PR #<n> into `,
   the title the twin wait matches); this run is excluded (its own review
   job is item 4).
10. **Approval reuse omits the context half of the review key.** `git
    patch-id` leaves out the whole `@@` line, so the same edits at other
    lines or in other functions (a retarget between bases can expose them)
    keep the patch id. The review key's second half is `ctx=`, the review
    job's `hunk_ctx` (the sha1 of one `<path><TAB><@@ line>` line per hunk).
    The gate computes it from the same `$BASE_SHA...$EVENT_SHA` diff and
    fails unless the approval's marker carries both `patch=` and `ctx=` of
    the change; the guard's reuse branch reuses the approval only under the
    same rule. A marker with no `ctx=` does not match.
11. **Re-adding code-review cannot recover the gate after a failed
    re-review.** Re-adding `code-review` took the guard's reuse branch and
    ended `skip=reviewed` without a new verdict, so item 6 kept every retry
    red. The reuse branch now reads the same history as the gate (this
    workflow's runs for this PR on the head, their `Codex review` jobs,
    through the Actions API with the job's own token): when one completed
    `failure`, `cancelled` or `timed_out` after the approval was submitted,
    it does not reuse the approval, sets `again` (so no approval of another
    head is carried either) and codex reviews the head and posts a fresh
    verdict, which item 6 then reads as newer than the failure.
12. **Keep the Actions credential header until approval-reuse checks
    finish.** Item 11's history lookup calls `gha()`, which reads its
    `Authorization` header from `$WORK/gha.hdr`, but the template removed
    that file right after the twin wait, so on GitHub an already-approved
    head with matching patch and ctx reached the lookup with no header,
    answered 401 and turned the required gate red, and re-adding
    `code-review` repeated it. The header is now removed by an `EXIT` trap
    set where it is written, so every `gha()` call of the guard step sees it
    and it is gone on every exit (`exit 0`, `exit 1`, `die`); the template's
    `rm -f` after the wait is dropped. The gate job reads no `gha.hdr` (it
    passes its token inline).
