# #779: a repeated session proposal applies once across a leader change

Objective: prove on an in-process three-replica shard that a session retry with
the same (clientID, seriesID) sent to a new leader after a leadership transfer
is applied once and answered with the first result, and that a retry below the
session's responded-to watermark is refused with `*SessionExpiredError`.

Existing unit coverage (single process, no leader change):
`pkg/internal/session/manager_test.go:115` (CheckDuplicate),
`pkg/internal/rsm/statemachine_test.go:2590` (in-batch duplicate),
`pkg/host_test.go:3208` (ResultSessionExpired → SessionExpiredError).

Slice 1 (this lane): `pkg/session_retry_leader_change_test.go`, reusing the
three-host helpers of `pkg/wireswitch_nextwire_test.go` with a counting SM:
- TestSessionRetry_LeaderChangeAppliesOnce
- TestSessionRetry_BelowRespondedToIsSessionExpired

Out of scope: wire/on-disk formats, production code unless a test fails.

## Review fix

1. Apply counts are checked only after every replica's ShardInfo.LastApplied
   reaches the log index of the final proposal (recorded by the counting SM on
   the leader), so a duplicate apply on a follower cannot hide behind the count.
2. The below-watermark test commits series 3 before the transfer, so the
   replicated RespondedTo is 2 and the series-1 retry is strictly below it;
   the live session then proposes series 4 and every replica applies 4 entries.
