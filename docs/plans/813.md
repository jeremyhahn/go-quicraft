# #813: Drain finishes in-flight requests, refuses new ones, Close follows

Objective: prove on an in-process single-replica shard that `Host.Drain`
lets in-flight `SyncPropose` calls finish, refuses every later one with
`ErrDraining`, is safe to call twice, and that `Close` then returns
promptly without leaking goroutines.

Slice 1 (this lane), test in `pkg/host_drain_test.go`:
- 16 goroutines loop on `SyncPropose` and are all making successful calls
  before `Drain` is called while they run.
- A call that starts before Drain returns ends in success or `ErrDraining`.
- A call that starts after Drain returns fails with `errors.Is(err, ErrDraining)`.
- `IsDraining` is true; a second `Drain` returns nil.
- `Close` returns within 5s; the goroutine count goes back to its baseline.

If a request path is found that ignores the drain: commit a failing test,
then the fix in `pkg/host.go`.

Out of scope: drain of reads, snapshots and sessions (covered in
`pkg/host_test.go`); multi-host transport drain.

## Review fix

- Held proposal: a state machine whose Update blocks on a channel for a
  marker command holds one admitted `SyncPropose`. Drain is started and is
  checked to still be blocked; the proposal is released, and it must
  complete before Drain returns (pendingOps is non-zero when Drain starts).
- Bounded cleanup: the test cleanup's `Close` runs in a goroutine with a
  deadline, and is skipped once the explicit `Close` attempt has timed out,
  so a hung Close cannot join the stuck stopOnce and hang the test binary.
