# #953: leader-change events across a real leader transfer

Refs #744 (v1.0.0 bar test gap).

## Objective

`config.EventListener` documents `OnLeaderUpdated` (fires on every leader
update, LeaderID 0 when none is known), `OnLeaderLost` (fires when this
replica was the leader and no longer is) and `OnCampaignLaunched` (fires when
this replica starts an election). The existing tests drive the callbacks with
a fake engine; none asserts them across a real leadership change on several
Hosts. This slice adds that test.

## Slices

1. `docs: plan for #953` — this file.
2. `test:` — `pkg/leader_change_events_test.go`,
   `TestLeaderChangeEvents_TransferFiresDocumentedEvents`: a three-Host mTLS
   cluster (the `newTransferCluster` pattern) with an `EventListener` per Host
   recording every event under a mutex. It asserts:
   - (a) once every Host agrees on leader L at term T, every Host's most
     recent `OnLeaderUpdated` for the shard names L and T;
   - (b) after `RequestLeaderTransfer` to follower F: L's Host fires
     `OnLeaderLost` exactly once with its own replica ID, F's Host fires
     `OnCampaignLaunched` at least once with a term above T, and every Host's
     most recent `OnLeaderUpdated` names F at a term above T;
   - (c) no Host other than L's fires `OnLeaderLost` for that change;
   - (d) a proposal after the transfer commits, and no further `OnLeaderLost`
     or `OnCampaignLaunched` fires during two idle election timeouts.
   Waits are bounded condition polls under a context deadline; no bare sleep.
3. Per divergence from the docs: a failing `test:` commit, then a `fix:` in
   `pkg/host.go` (or a doc correction in `pkg/config/hostconfig.go` where the
   code is right and the doc wrong).

## Out of scope

- `OnLeaderReady` ordering (covered by `host_leader_ready_test.go`).
- Elections caused by partition or Host loss; membership changes.
- Any wire or on-disk format change.
