# Plan for #940: a second membership change while one is uncommitted

Tracked under #744 (v1.0.0 bar test gap).

## Objective

Prove at the public Host API that a membership change proposed while an
earlier one is still uncommitted is refused with `ErrRejected` (as
docs/membership-changes/user.md says), that the refusal is definite
(`MaybeApplied` false) and leaves the membership unchanged, and find out what
`Config.OrderedConfigChange = BoolPtr(false)` actually does.

## Slices

1. This plan.
2. `pkg/host_ordered_config_change_test.go`, on one transportless Host:
   - (a) `SyncRequestAddNode` of replica 2 (never started) commits; the
     shard now needs two votes, so nothing further can commit;
   - (b) `RequestAddNode` of replica 3 returns a `*RequestState` whose
     change is appended but cannot commit;
   - (c) while (b) is pending, `RequestAddObserver` and `RequestRemoveNode`
     each fail with an error matching `ErrRejected`, `MaybeApplied` false,
     and `ShardMembership` is unchanged;
   - (d) the same sequence with `OrderedConfigChange: config.BoolPtr(false)`.
   CheckQuorum is disabled on the test shard so the lone live voter keeps
   leadership after the voting set grows to two.
3. Outcome of (d). raft's pending-change gate
   (pkg/internal/raft/raft.go, handlePropose) is unconditional and
   `Config.GetOrderedConfigChange` is read by nothing outside pkg/config, so
   (d) is expected to be refused exactly as (c). The gate stays (it is a
   Raft safety requirement); the field's doc comments in
   pkg/config/config.go are corrected to say membership changes are always
   serialised and the field has no effect, and Validate's warning for
   `BoolPtr(false)` says the same. docs/membership-changes/user.md
   already describes the serialised behaviour and is left as is unless it
   says otherwise.

## Out of scope

- Removing or making the pending-change gate optional.
- Removing the `OrderedConfigChange` field (an API change).
- Multi-host or transport-backed membership tests.
