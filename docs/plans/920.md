# Plan for #920: NodeHost snapshot export and import

Refs #744 (v1.0.0 bar test gap).

## Objective

Prove that a snapshot exported from a dragonboat-compatible `NodeHost`
imports into a fresh `NodeHost`, which starts the shard with the same state,
as `contrib/dragonboat/README.md` and `docs/multi-group-host/api.md` say.
Until now only the error paths of `NodeHost.ExportSnapshot` and
`NodeHost.ImportSnapshot` were tested.

## Slices

1. This plan.
2. `contrib/dragonboat/nodehost_export_import_test.go`, built on
   `newTestNodeHost`, `startTestShardWith` and `testStateMachine`:
   - (a) NodeHost A: 20 `SyncPropose`, `SyncRequestSnapshot`, then
     `ExportSnapshot` into a `bytes.Buffer` returns nil and a non-empty
     artifact.
   - (b) A's shard stopped, `ImportSnapshot` of the same artifact into A
     returns the documented result for an index already recorded
     (`*ImportSnapshotOutOfDateError` or `*ImportSnapshotDirExistsError`),
     never a panic.
   - (c) fresh NodeHost B (shard bootstrapped and stopped, as the
     disaster-recovery flow says): the import succeeds and `StartReplica`
     then `SyncRead` returns the last proposed value. If it instead fails with
     `ErrImportLayoutUnknown`, the README says how a NodeHost user imports on
     a fresh host.
   - (d) importing into a running shard fails with `ErrInvalidOperation`; a
     truncated artifact fails with `ErrSnapshotCorrupt` or
     `*SnapshotArtifactError`, and B's shard then starts empty.
3. Per divergence from the docs: a failing `test:` commit, then a `fix:`
   commit in `contrib/dragonboat/nodehost.go` (or a README correction when
   the doc is what is wrong).

## Out of scope

- The Host-level export/import rules themselves (covered in `pkg`).
- Import options (`WithImportDataDir`, membership overrides) through the
  NodeHost, which does not accept them.
- Any wire or on-disk format change.
