# #1104 — FollowerRead stale value; leader transfer misses 1s (main red)

## Leader transfer (`TestLeaderTransfer_MovesLeadershipAndKeepsEveryAcknowledgedWrite`)

Cause: under `-race` load an election can overtake a requested transfer, so a
different replica leads in a higher term when the 1s deadline expires. That is
not a transfer bug: Raft allows an election to win over a pending transfer.

Fix (test): `transferNext` asks the new leader to make the same transfer again,
up to 5 times, when an intervening election superseded the request.
Measured: `go test -race -count=100 -run TestLeaderTransfer_MovesLeadership ./pkg/`
passes 100/100.

## FollowerRead (`TestFollowerRead_RealFollowerReturnsEveryWriteCommittedBeforeTheRead`)

Cause (fr1104d, measured): the test's acknowledgement index was too low, not
FollowerRead. `tryPut` returned the leader's `CommittedIndex()` after
SyncPropose, but the commit worker's piggyback path (`commitUpdateLocked`,
pkg/internal/engine/commit.go, `GetPiggybackUpdate`) extracts committed
entries and hands them to apply without `publishLogMarkers`; only the step
worker publishes (step.go after GetUpdate, and each tick). So a write can be
applied and acknowledged while the leader's published commit is one entry
short. The diag showed it directly: "ack leader 2 index 52; r1 commit=52
applied=52; r2 (leader) commit=53 applied=53" with the put at index 53. The
follower correctly served its known commit 52. Before the fix the 100-run
measurement failed often (both subtests: "key not found" and "older than").

Ruled out: step.go:609 publishes before the update reaches apply; follower
commit advances in raft.go (`handleAppend` caps at the last new entry,
heartbeat at the current-term tail) are safe; `Host.FollowerRead`,
`OnApplied` (lastApplied stored before proposals complete) and
`kv.ConcurrentStore.Update` are correctly ordered.

Tried and refuted (fr1104d): returning the leader's `ns.lastApplied` from
`tryPut`. Host `OnApplied`'s ordinary path completes each proposal inside its
loop (`completeProposal`, host.go ~1996) BEFORE `completeAppliedReads` stores
`ns.lastApplied` (host.go ~2149), so the ack can also precede the leader's
applied index. Measured: "put 29 ... commit index 33 known; leader r2 c=34
a=33; follower c=33 a=33; retry 100ms later = value-29, follower c=34".

Next slice (decide): the test needs an index the acked write is at or below.
Options: (a) library: store `ns.lastApplied` (and publish markers in
`commitUpdateLocked` after `GetPiggybackUpdate`) before completing proposals,
so "acked => leader's applied/commit covers it"; host.go is in the File map,
commit.go is not. (b) test: after the ack, take the index from a ReadIndex
round on the leader (any read index taken after the ack covers the write).
Prefer (a) if moving the store before completion is safe (completion must not
run under pendingReadsMu); then test commit + fix commit. `diag` is still in
the test; remove it before promoting.

Engine part of (a) (outside this lane's File map): the engine could
call `node.publishLogMarkers()` in `commitUpdateLocked` after
`GetPiggybackUpdate` (raftMu is held there), so a leader's published
`CommittedIndex` never lags its applied index. FollowerRead uses only the
local replica's own published commit and waits for apply to reach it, so the
lag delays nothing it promises; any caller comparing a leader's published
commit with its applied index can see the lag.
