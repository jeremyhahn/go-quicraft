# #1104 — FollowerRead stale value; leader transfer misses 1s (main red)

## Leader transfer (`TestLeaderTransfer_MovesLeadershipAndKeepsEveryAcknowledgedWrite`)

Cause: under `-race` load an election can overtake a requested transfer, so a
different replica leads in a higher term when the 1s deadline expires. That is
not a transfer bug: Raft allows an election to win over a pending transfer.

Fix (test): `transferNext` asks the new leader to make the same transfer again,
up to 5 times, when an intervening election superseded the request.
Measured: `go test -race -count=100 -run TestLeaderTransfer_MovesLeadership ./pkg/`
passes 100/100.

## FollowerRead (`TestFollowerRead_RealFollowerReturnsEveryWriteCommittedBeforeTheRead`)

Still open. It reproduces in 2 of 100 `-race` runs, in the *sequential*
subtest "each put is visible on every follower once it knows the commit"
(`put 47: FollowerRead on replica 2: kv: key not found`). The steps are:
SyncPropose on the leader, then `awaitCommitted(follower, c.committed(leader))`,
then FollowerRead.

Library paths checked, all correctly ordered:
- `Host.FollowerRead` (pkg/host.go) waits for `ns.lastApplied >= engNode.CommittedIndex()`.
- engine apply (`apply.go`): `sm.Apply`, then `OnApplied`, which stores
  `ns.lastApplied` under pendingReadsMu, then `node.lastApplied`.
- `kv.ConcurrentStore.Update` writes the buckets synchronously under their locks.
- The published `Node.committedIndex` comes from `Peer.LogMarkers` (log.committed).
  It is published in step.go right after `GetUpdate` and on every tick, so it is
  never ahead of the raft log.
- A proposal on a non-leader is forwarded (raft.go `case proto.Propose`).
- `NotifyCommit` is off by default, so SyncPropose completes on apply.

fr1104c measurements (100 `-race` runs, before the test change): one failure,
in the *concurrent* subtest: both followers read 75 five times in a tight loop
while 76 was acked "at commit index 129". The whole test took 1.49s and one
leader held term 2 throughout, so no 3s SyncPropose timeout or election was
involved.

Test change (committed, wip): every writer attempt writes a fresh value; a
value whose SyncPropose failed may land late and is accepted out of order. This
is sound (a failed proposal has an unknown outcome), but it does NOT explain
the failure above. The sequential subtest now prints each replica's
commit/applied/leader state plus a read retried after 100ms (`diag`).

Leading hypothesis (next slice): the leader's ack index is too low. The
`tryPut` index is `CommittedIndex()` on the leader, which `publishLogMarkers`
sets at step.go:609 (after GetUpdate) and step.go:414 (each tick). If the apply
worker can apply the entry and complete SyncPropose before the step worker
publishes the commit that covers it, the test's index misses the write, and a
follower at that index reads the older value. Check: read step.go around 560–
620 (Serena `find_symbol` on the enclosing function) to see whether the
committed entries are handed to apply before line 609. If they are, fix the
test (take the index from the max commit over all hosts *after* the leader's
published commit reaches its applied index, i.e. wait for
`committed(li) >= lastApplied(li)` before returning), since FollowerRead's
contract is relative to the commit the follower knows. If not, fall back to
hypothesis 2: the follower commit cap in `handleAppend` (heartbeat already
requires the tail term to equal the current term, which looks safe).
