# Plan: #934 scheduled key rotation with a real seal barrier

Refs #744 (v1.0.0 bar test gap).

## Objective

Prove that a Host configured with a real `seal.Barrier` (software strategy,
initialised and unsealed, with a `StatePersister`), `KeyRotationInterval` 1s
and `MaxRetainedEpochs` 2 rotates its key on the schedule documented in
pkg/config/hostconfig.go and docs/seal-barrier/user.md, and that every entry
and snapshot written under any epoch stays readable after a restart.

## Slices

1. `docs: plan for #934` — this file.
2. `test:` pkg/host_key_rotation_live_test.go, `TestKeyRotationLive_*`:
   - (a) `CurrentEpoch` advances at least three times within a bounded wait
     while a single-replica shard serves proposals;
   - (b) a value proposed under each observed epoch reads back with
     `SyncRead`;
   - (c) after `SyncRequestSnapshot`, more proposals, `Close`, and a new Host
     on the same directories with a new barrier loaded from the last persisted
     `SealedRootKey` and unsealed, every value reads back;
   - (d) the last persisted `KnownEpochs` still holds every epoch a live WAL
     record or the retained snapshot was sealed under, so (c) never fails to
     decrypt.
3. Per divergence from the docs: a failing `test:` commit, then a `fix:`
   commit in pkg/host.go (or a doc correction in docs/seal-barrier/user.md
   when the code is right).

## Out of scope

- Multi-replica rotation, transport encryption, invocation-threshold
  rotation, and any change to a wire or on-disk format version.
