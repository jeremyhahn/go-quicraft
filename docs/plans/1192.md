# #1192: worker-side configChangeIndex check for add node, observer and witness

## Objective

`Host.RequestAddNode`, `RequestAddObserver`, `RequestAddWitness` and their
`WithIdentity` forms carry `configChangeIndex` as
`proto.ConfigChange.ConfigChangeID`. Today only `Host.requestConfigChange`
compares it, against an atomic copy, before the change is queued. A second
membership change can commit between that host check and the worker's
proposal, and the worker validators (`validateAddNode`,
`validateAddNonVoting`, `validateAddWitness` in
pkg/internal/raft/membership.go) never compare the index, so a stale add can
enter the log. `validateUpdateWireVersion` already does the exact match.
Also, 0 means "skip", so an add against the initial configuration
(ConfigChangeID 0) can never be checked.

## Design

1. Worker check: the three add validators refuse a bound change whose
   `ConfigChangeID` differs from `m.configChangeID`, with the same stale
   error class the update-wire-version path uses. The refusal surfaces at
   the Host as `*StaleConfigChangeError` (`errors.Is(err,
   ErrStaleConfigChange)`), not as a pending-change error.
2. Bound form at 0: a variadic `...ConfigChangeOption` on the RequestAdd*
   calls (existing callers compile unchanged). The bound option sets an
   in-memory must-match marker that reaches the worker check. The marker is
   not part of the wire encoding: it is excluded from Marshal, Unmarshal and
   Size, so no wire or format version changes.
3. A change is bound when `ConfigChangeID != 0` or the marker is set. An
   unbound add (index 0, no option) behaves as today.
4. Doc comments: correct the "false negatives cannot occur" comment in
   `requestConfigChange` and the RequestAdd* doc comments to describe the
   worker check and the bound form.

## Tests (test commit first, then the fix)

- pkg/internal/raft/membership_test.go: table tests for the three
  validators: bound change with a differing ConfigChangeID is refused;
  matching ID accepted; ID 0 unbound accepted; ID 0 bound refused when the
  membership's ID is > 0.
- pkg/host_configchange_worker_test.go (new), on the real Host: an add is
  checked against C, a gate holds it between the host check and the worker
  proposal, a second add commits; on release the first add is refused with
  `ErrStaleConfigChange` and nothing enters the log. Voter, observer and
  witness; from C > 0 and from the initial configuration with the bound
  form at 0. Unbound add at index 0 is accepted as before.

## Status: done

- Raft refusal is typed `*raft.StaleConfigChangeError{Expected, Got}`
  (`errors.Is` `raft.ErrStaleConfigChange`), mapped in
  `translateProposalError` to `*StaleConfigChangeError{ShardID, Expected, Got}`.
- Bound form at 0: `WithBoundConfigChangeIndex()`; the Host binds the
  proposal key in `Peer.boundConfigChanges` before delivery (unbound only
  when registration or delivery is refused; see Review fixes);
  `raft.validateProposedConfigChange(key, cmd)` consumes it and sets the
  marker. No wire change.
- Witness add from index 0 at the Host: the witness kind starts from a shard
  whose bootstrap `config.WitnessConfig` relaxes the full-replica majority,
  so no policy change commits first and the bound and unbound witness adds
  run from ConfigChangeID 0. The host tests are named `TestConfigChange_*`
  (`WorkerRefusesStaleIndex`, `UnboundZeroIndexUnchecked`,
  `BoundZeroIndexAccepted`) so the `-run` pattern above reaches them; each
  has voter, observer and witness subtests (stale-index: from C and from 0).

## Review fixes

1. Expiry dropped the binding while the entry could still reach Raft: the
   deadline sweep fails a pending proposal without removing it from the
   queue. The Host's failure hook no longer unbinds; it unbinds only on
   refused registration or delivery. raft consumes the binding whenever it
   takes the entry: on validation, and on any refused Propose
   (`Peer.releaseRefusedBindings` via `raft.takeBoundConfigChanges`). An
   entry left untaken in a closed queue dies with its Peer. Test:
   `TestConfigChange_BoundZeroExpiredBeforeWorkerStaysBound` (failed before
   the fix: the expired add committed).
2. Forwarding to a new leader dropped the bound-zero constraint (the binding
   is local; the entry encodes index 0). A follower or candidate now refuses
   a Propose carrying a locally bound config change with
   `raft.ErrBoundConfigChangeNotLeader` (`errors.Is`
   `ErrStaleConfigChange`), forwards nothing and consumes the binding; the
   Host maps it to the public `ErrStaleConfigChange`. The batch is refused
   whole, as for `ErrPendingConfigChange`. Unbound changes forward as before.
   Test: `TestRaft_BoundConfigChangeNotForwarded` (failed before the fix:
   the entry was forwarded).
