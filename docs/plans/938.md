# #938: MaxApplyWorkers bounds concurrent Updates across shards

Refs #744 (v1.0.0 bar test gap).

## Objective

Prove at the Host level that `HostConfig.MaxApplyWorkers` bounds how many
state machine `Update` calls run at once, and that one shard's `Update`
calls never overlap.

The engine builds one apply worker per `NumWorkers`, and each apply worker
holds its own semaphore of `MaxApplyWorkers` slots
(`pkg/internal/engine/engine.go`, `newApplyWorker`). The bound is therefore
per apply worker: with `NumWorkers` 1 the Host-wide bound is exactly
`MaxApplyWorkers`.

## Slices

1. `docs: plan for #938`: this file.
2. `test: MaxApplyWorkers bounds concurrent Updates ...`: new
   `pkg/host_apply_workers_test.go`. A Host with `NumWorkers` 1 and
   `MaxApplyWorkers` 2 runs eight single-replica shards whose state machine
   `Update` records the running count (host-wide and per shard) and blocks
   on a release channel for proposal entries. One proposal per shard:
   - (a) running `Update` calls reach 2 and never exceed 2;
   - (b) no two `Update` calls for one shard overlap;
   - (c) after release every proposal completes and each entry is applied
     exactly once;
   - (d) `Close` returns within a bounded time with no `Update` running.
3. If the code departs from the docs: a failing `test:` commit, then a
   `fix:` commit in `pkg/internal/engine/apply.go`. If the doc is what is
   wrong, a `docs:` commit in `pkg/config/hostconfig.go`.

## Out of scope

- Changing the bound to be host-wide rather than per apply worker.
- Concurrent or on-disk state machine variants.
- Any wire or on-disk format change.
